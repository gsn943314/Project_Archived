### 3. Shortest walkable path from A to B

- `NavMeshBoundsVolume_Pathfinding` covers the floor to generate the NavMesh.
- `BP_PathfindingCharacter` is an AI-controlled character using the Quinn model. It uses `AI MoveTo` to walk to `TargetPoint` (point B).
- The path is computed on the NavMesh (A*): the shortest walkable route, not the straight-line distance.
- First test: straight-line distance 1521 cm, walkable path 2572 cm; the character walks around obstacles and reaches B in about 6 s.

### 4. Top-down camera and game loop

Driven mainly by `BP_PathfindingPlayerController`, with a `Phase` variable:

| Phase | State | Behaviour |
|-------|-------|-----------|
| 0 | PLANNING | Top-down camera (`OverviewCamera`); every Tick draws a path preview with `FindPathToLocationSynchronously`: green = reachable, red + BLOCKED = blocked |
| 1 | RUNNING | `SetViewTargetWithBlend` switches the camera to the character and follows it |
| 2 | ARRIVED / BLOCKED | On arrival, waits for the player to press RESET; when blocked, runs `ResetRun` automatically after 2.5 s |

- Editable obstacles are `BP_EditableObstacle`, tagged `Editable`, with the purple material `MI_EditableObstacle`.
- Controls: `W` / `E` / `R` switch between move / rotate / scale, adjusted by mouse drag or wheel. Minimum scale 0.15.
- UI is `WBP_PathfindingHUD`: PLAY and RESET buttons plus Phase, Path, Selection and Mode text fields.
- Added `BP_PathfindingGameMode`, used only as this level's GameMode override.
- NavMesh Runtime Generation set to **Dynamic**, so the path is recomputed within 2 s after an obstacle moves (test: 2687 → 2650 cm).

### 5. Single-path puzzle level `Lvl_PathfindingPuzzle`

New level `/Game/Project/Maps/Lvl_PathfindingPuzzle`, created from `Template_Default` without World Partition.

- The maze is generated by a Python script: 13 × 10 cells of 350 cm, 18 corridor cells, 18 merged wall segments, 6 corners, and a ramp that goes up then down in the middle.
- Point A at `(-1750, -1225)`, point B at `(1750, 1225)`, a purple gate at `(700, 525)` that fully blocks the corridor.
- The corridor is a staircase shape that keeps getting closer to B. When B is unreachable the NavMesh returns a **partial path** ending at "the reachable point closest to B"; the staircase shape guarantees that point is right in front of the gate. An S-shaped route that doubles back would stop the character in the wrong place.
- `StartRun` now computes the path first, takes the last point of the partial path as `RunDestination`, then `AI MoveTo`s there. `NotifyRunFinished` treats "2D distance to B ≤ AcceptanceRadius + 80" as a real arrival.
- Art: added `MI_MazeWall` (dark), `MI_MazeFloor` (light corridor), `MI_MazeBackdrop`, and an unbound `PostProcess_FixedExposure` (auto-exposure min/max locked at 1.0, bias −0.5).

**Pitfalls**:

- The walls had a dark material but still looked light grey. I first suspected the material wasn't applied, but it was correct; auto-exposure was brightening the image.
- After locking exposure with a PostProcessVolume, a bias of −1.5 was too dark; settled on −0.5 and gave the corridor floor its own brighter material.

### 6. Crash investigation and hidden-risk scan

The Editor crashed during automated testing. The log `~/Library/Logs/Unreal Engine/mcptestEditor/mcptest-backup-2026.11.12-21.55.57.log` showed:

```text
Assertion failed: GameViewport.IsUnique()  [SLevelViewport.cpp:5242]
SLevelViewport::EndPlayInEditorSession ← UEditorEngine::EndPlayMap
```

The test script called `StopPIE` and then immediately `StartPIE` in the same Python call; the previous PIE viewport was referenced before it was cleaned up, triggering the assertion. This came from the test method, not the game logic. The last save before the crash (16:55) was on disk; nothing was lost.

I also scanned the logs and Blueprint source:

| Check | Result |
|-------|--------|
| Blueprint Runtime Error / Accessed None | 0 |
| `ResetRun` order | `EnterPlanning` (Phase = 0) first, then `ResetToStart`. The OnFail fired when `StopMovement` interrupts movement is filtered by the `Phase == 1` check, so it is not mistaken for BLOCKED |
| Pressing RESET or PLAY during the 2.5 s BLOCKED wait | After the Delay it re-checks `Phase == 2`, so no double reset |
| Minimum scale | 0.15; never 0 or negative |
| NavigationSystem CDO ensure (21:35) | A handled ensure caused by how Python was called in an old-level test; not a crash |
| NavMesh "3 tile limit reached" (21:18) | Only in the old FirstPerson level, not the new one |
| Phase turning RUNNING by itself within 3 s of PIE start | The same Blueprint measured Phase 0 at 2 s; only materials and exposure changed afterwards. Judged to be an external action, not an auto-start bug |

## Problems

| Problem | Solution |
|---------|----------|
| After editing a Blueprint, the character in the FirstPerson level (World Partition) broke during reinstancing and fell out of the world | Placed a new character at the same position, rotation and Target; on save World Partition deleted the old external actor package. New levels use a non-World-Partition template |
| Path not updating after moving an obstacle | NavMesh Runtime Generation set to Dynamic |
| Character stopping in the wrong place when B is blocked | Corridor reshaped into a staircase that approaches B, and the character walks to the end of the partial path |
| Dark materials appearing light grey | PostProcessVolume locking exposure, bias −0.5 |
| `Unclosed parenthesis` on DSL write | Added the missing closing parenthesis and rewrote; compiled |
| Back-to-back `StopPIE` → `StartPIE` crashing the Editor | Stop and start PIE in separate calls, waiting for PIE to fully end |
| After restarting the Editor the MCP listener failed to bind port 8000 (`HttpListener unable to bind to 127.0.0.1:8000`), `unreal-mcp` returned ECONNREFUSED | A leftover process from the crash may still hold the port. Wait for it to release, or change the port in Editor Preferences → Model Context Protocol |
