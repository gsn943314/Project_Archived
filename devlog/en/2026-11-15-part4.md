## Completed

### 1. Getting caught by the beast always triggers knockdown + Glitch (Level 1)

- `OnCaught`'s `bCaught` is a once-per-run flag that was never reset, so from the second run on getting caught did nothing and the fox was stuck in RUNNING. `StartRun` now resets it.
- The chaser's hit distance went from capsule radius + 60 cm to + 125 cm (about 170 cm). The beast model is large; when it pressed alongside or diagonally against the fox, the center distance often stayed outside the range.
- The BLOCKED branch of `OnRunFinished` first checks for a `BP_EnemyChaser` within 2 m: if there is one, it counts as caught. 2 m avoids treating a beast behind a fence (about 4.4 m away) as a hit.

### 2. Glitch trigger `BP_GlitchSpot`

- When the fox enters the radius in Phase 1, the `Target` art tears for `GlitchDur` seconds (implemented in `BP_PortalGlitch.SetupActor`). With `ScreenAmt` > 0 a full-screen Glitch plays too.
- If the spot has `Say:` tags, the first pass stops the fox, turns it to the Target and plays the lines (chasers pause). It only counts as said once all lines finish; being caught, RESET or BLOCKED midway doesn't count.
- Two in Level 1:
  - `GlitchSpot_Camp`: at (1400, -875), radius 3 m, Target is the tent, two lines.
  - `GlitchSpot_Arch`: Target `Art_ExitArch`, radius 9 m, tears for 4 s, plus full-screen strength 0.45.

**Pitfalls**:
- On the first repro the spots didn't exist in the PIE world at all: the level open in the Editor didn't have them, probably undone.
- The arch was first mis-targeted as `Art_RightLandingWall`; corrected to `Art_ExitArch` after the user pointed it out. The spot was at platform height, so the fox had to climb the stairs before triggering it, too late; moved to z 150 with a bigger radius.
- The tent spot was centered on the tent with a 6.5 m radius. The stair entrance was right at the edge, so when the fox turned up the stairs early it grazed past, occasionally not triggering. The user's Output Log had `BeginPlay` but no `talk START`, which confirmed it; the spot was moved to the corner at the stair entrance.
- Added Output Log traces: `GlitchSpot BeginPlay` / `talk START` / `talk END talked=`.

### 3. Creator Access HUD (design A)

- Textures imported to `/Game/Project/Art/UI/CreatorHUD/`.
- `WBP_PathfindingHUD` gained `CreatorCard`, containing:
  - Background card and title "CREATOR ACCESS"
  - Goal text `GoalText`
  - Play / Reset buttons tinted through a shared mask: enabled #EDFC35, disabled #7D8599
- Reuses the existing `PlayButton` / `ResetButton`, so no controller code changes.
- The old info `Panel` is Collapsed and kept for debugging.

### 4. Dialogue: typewriter text, click to advance, Storybook look, speaker nameplate

- `BP_DialogueDriver`, spawned by `BP_PathfindingGameMode`, handles every `WBP_Dialogue` on screen each frame:
  - Types 45 characters per second.
  - Clicking the box: while typing, shows the whole line immediately; when done, sets `bAdvance` and the caller moves to the next line.
  - Three callers wired to `bAdvance`: `BP_GlitchSpot`, `BP_FoxLook`, the controller's `UpdateHint`.
- Look switched to Storybook Dialogue A:
  - Beige base panel.
  - Green nameplate fixed at 334×120, keeping the original proportions; long names are shrunk by a `ScaleBox` (shrink only).
  - Brown V-shaped continue arrow that blinks once the line finishes.
  - Version C textures imported too, not used yet.
- Nameplate rules:
  - `bSystem` (`SYS:` lines in `BP_FoxLook`) shows `SYSTEM`.
  - Everything else is the fox, shown as `BP_GreyFox` / `SK_Fox_WIP` / `Fox` based on `BP_FoxLook.Stage`.
- Text colour is set centrally by the Driver: fox dark brown, system dark green.

**Pitfalls**:
- The first nameplate used auto width with 9-slice stretching and the art got distorted; reverted to fixed original proportions.
- The user felt the original grey-model name `BP_PathfindingCharacter` was too long; switched to shorter fake asset names.

### 5. Level 0 fox monologue on entering greybox (`BP_IntroTalk`)

- When the opening cutscene ends and greybox starts for the first time, it waits 1.6 s for the transition Glitch, then plays the 4 `Say:` lines on `IntroTalk_Greybox` in order, e.g. "Where am I?", "Why is everything grey?".
- Plays once per level; pressing PLAY ends it.

### 6. Rock beast material breaking

- `M_RockEnemy` was used on a skeletal mesh without **Used with Skeletal Mesh** checked. The Editor only auto-sets it in memory and doesn't save, so it worked intermittently on my machine and showed the default grey checker for teammates.
- Checked and saved. Also checked every other skeletal mesh material in the project; this was the only one missing it.

## Problems

| Problem | Solution |
|---------|----------|
| Getting caught does nothing from the second run on, stuck in RUNNING | `StartRun` resets `bCaught`; hit distance raised to capsule radius + 125 cm |
| Tent dialogue occasionally not triggering | Spot moved from the tent center to the stair-entrance corner, radius 3 m |
| Editor crash (`PlayLevel.cpp:558`, PIE object referenced by TransBuffer) | Editing game objects with `execute_python` during PIE records them in Undo, which asserts on StopPIE. Only read-only queries during PIE; trigger events with `ke <actor> <event>` |
| Dialogue speed-up had no effect after the crash | `BP_DialogueDriver` had been saved as an empty shell. DSL Write compiles but doesn't save; now `save_asset` immediately after every Blueprint edit |
| Enemy material broken on teammates' machines | Checked Used with Skeletal Mesh on `M_RockEnemy` and saved |
| Nameplate text off-center, overflowing, stretched | Fixed-proportion nameplate, `ScaleBox` to shrink text, aligned with the dialogue text |
